## 2. ABSOLUTE ENGINEERING RULES (override everything else)
2.1 Preserve the project: do not rebuild; do not replace the architecture without approval; no unnecessary dependencies, frameworks, services or infrastructure; no broad refactors for aesthetics; no features outside the product scope; do not remove functionality because it is hard to maintain; preserve behaviour unless a verified defect or approved requirement justifies a change; prefer minimal, targeted, defect-driven changes.
2.2 Git safety. Before any work: inspect branch, `git status`, modified/staged/untracked files, recent commits, all worktrees and branches; record the baseline. NEVER: `git reset --hard`; `git clean`; force-switch branches; overwrite uncommitted work; discard another agent's changes; commit another agent's work without review; merge or push without explicit human approval; deploy without explicit human approval; broad staging such as `git add .`. Stage explicit files only after authorization. Do not assume the primary repository is clean.
2.3 `digest.txt` is STRICTLY OFF-LIMITS: do not open, read, search, hash, modify, rename, move, delete, stage or commit it, and do not run commands or scripts that indirectly process it. Applies to every agent, reviewer, script and workflow.
2.4 Database safety: never run destructive scripts against an unknown MongoDB URI; never use the production database for testing; never use a persistent development database as a test database; use isolated MongoMemoryServer harnesses; run tests sequentially where ports, rate limiters, processes or shared resources could conflict; verify environment variables before running scripts; never run legacy seed/backup/restore/cleanup scripts without inspecting them and obtaining approval.
2.5 Dependencies and environment: do NOT install dependencies, upgrade dependencies, modify lockfiles, download browser binaries, change environment settings, change deployment settings or introduce infrastructure without approval. Dependency/security audits are allowed within approved scope.
2.6 Evidence: classify every finding as one of Verified defect / Verified security vulnerability / Verified incomplete feature / Verified UX problem / Verified performance problem / Not reproduced / Partially resolved / Fully resolved / Blocked / Requires product-policy decision / Superseded. Never report a feature as working because its code exists; never report a fix as complete because an agent changed a file. Completion requires verification evidence.
