# DEP-01 - Dependency remediation PLAN (finding NEW-12) - 2026-11-01

Role: Security Lead. PLAN ONLY. I ran no npm command, edited no manifest or lockfile, and tested nothing. Everything below is from reading files (audit summary and saved JSON, the three manifests, lockfiles, and source under `backend/src` and `frontend/src`). Advisory text: I read advisory TITLES and version ranges from the saved JSON only, not full advisory bodies, so "exploitable here" is an inference from how the code uses each package, not a test (charter section 21).

## 0. Headlines
1. **Almost everything is fixable without a semver-major change.** Every flagged package except `zod` and `react-router-dom` is inside the range already declared in its manifest, so a targeted lockfile refresh would pick up the fix. Verify this against the registry when the owner approves (I could not query it).
2. **proxy-addr: the smaller fix is a lockfile refresh of `proxy-addr` alone.** Express 4.22.3 declares `"proxy-addr": "~2.0.7"` (backend lockfile line 1905), which admits 2.0.8, the first fixed version (vulnerable range `>=1.1.0 <2.0.8`). No Express update and no `overrides` entry is needed. An Express update is the larger option (Express 4.22.x to a newer 4.x only if it exists; Express 5 is a major). An `overrides` entry is unnecessary and would add a manifest change that must be maintained.
3. **The root `package.json` is not used at runtime.** Its tar / @mapbox/node-pre-gyp findings come only from root `bcrypt`, which nothing imports (section 3). The root criticals are therefore not reachable in the running app.
4. **Several "production, high" findings are not reachable as the code reads today:** `multer` (the only upload router is deliberately unmounted, AUD-001), the `dompurify` critical (SEC-01), `zod` (no constrained collections in use).
5. **CI gate:** `.github/workflows/pr-checks.yml` runs `npm audit --audit-level=high` for frontend and backend. Both currently have high/critical findings, so the security job fails on any PR touching those folders until Batches 1 to 3 land. Owner should know that gate is red for dependency reasons, not code reasons.

Installed versions come from the lockfiles. "Fixed in" is the upper bound of the vulnerable range in the audit JSON (the first version above it); unverified against the registry.

## 3. Root manifest (`package.json`): tar (critical) and @mapbox/node-pre-gyp (high)

Question: is the root `package.json` used at runtime at all?

Evidence:
- Root dependencies: `@azure/storage-blob, bcrypt, dotenv, express ^5.2.1, mongoose, multer`. Backend dependencies are a superset except for `bcrypt` and carry Express `^4.18.2`, `bcryptjs`, `cors`, `helmet`, `jsonwebtoken`, etc.
- Every `require` in `backend/src` that I grepped for password hashing uses `bcryptjs` (`routes/auth.js:2`, `models/User.js:2`). A repo-wide search of `*.js|ts|tsx|cjs|mjs|json|yml` for the string `"bcrypt"` finds it only in `package.json:19` and `package-lock.json:12`. **Nothing imports `bcrypt`.**
- `tar` 6.2.1 reaches the root tree only through `bcrypt -> @mapbox/node-pre-gyp -> tar` (build-time prebuilt-binary download/extract during `npm install`). The root lockfile contains `bcrypt 5.1.1`, `@mapbox/node-pre-gyp 1.0.11`, `tar 6.2.1`.
- Node resolves `require` from the requiring file upwards: `backend/src/server.js` first looks in `backend/node_modules`. A root-only install could not run the server anyway: `cors`, `helmet`, `jsonwebtoken`, `bcryptjs`, `express-rate-limit`, etc. exist only in the backend manifest.
- Root scripts (`start`, `seed`, `backup`, `test:*`) are thin wrappers that call `node backend/src/...`; `dev` calls `start.js`, which spawns `backend/src/scripts/runWithMemoryDb.js` and `npm run dev` in `frontend`. Root also supplies `husky` + `lint-staged` (`prepare: husky`) for git hooks. The CI workflow installs only in `frontend/` and `backend/`.
- The root README says to run `npm install` at the repository root, so a root `node_modules` is installed on developer machines (that is why the root tree is audited).

Conclusion:
- **tar / node-pre-gyp / bcrypt in the root manifest are dead weight: not imported, not used by CI, not used to run the production server.** The tar advisories (hardlink path traversal / symlink overwrite on extract) fire only when extracting an attacker-controlled tarball; the only extraction is `node-pre-gyp` downloading bcrypt's own binary at `npm install` time, from the project's npm registry/GitHub release, on a developer machine. Practical exploitability: very low. Not determined: whether any deployment (Docker/Render/Azure) runs a root `npm install`; the repo has no deployment manifest (SEC-02), so I cannot rule it out.
- Smallest fix: **remove `bcrypt` from the root `package.json`** (one-line manifest edit plus regenerated lockfile; this deletes tar, node-pre-gyp and their transitive set at once). It is a manifest/lockfile change and needs owner approval; it is the *smaller and cleaner* fix compared to bumping tar/node-pre-gyp, which cannot be done independently because node-pre-gyp 1.x pins `tar ^6`. Alternative: `npm update` plus `overrides` for tar ^7 (breaking for node-pre-gyp; larger and pointless for an unused dependency).
- The other root findings (body-parser 2.3.0, brace-expansion 1.1.16, fast-xml-parser 5.9.3, follow-redirects, ip-address 10.2.0, multer 2.2.0, qs, and the Express 5 tree with proxy-addr 2.0.7) are the same class: a second, parallel install that the application does not load. If the owner removes duplicated runtime dependencies from the root manifest, these go with it. Root `multer` 2.2.0 is flagged on different advisories from backend's, still unreachable via the root tree.

Owner decision needed (not mine to make): D-xx candidate "Should the root manifest shed runtime dependencies (keep only husky/lint-staged and scripts)?" This is a repository-structure decision; the safest narrow version is only removing `bcrypt`.

## 4. Ordered batches with regression plans

Rule for all batches: one worktree, one harness run at a time (charter rule 5), no localhost:5000. Each batch needs owner approval to change manifests/lockfiles (rule 2 / charter 2.5). I do not run any of this.

**Batch 0 - Owner decisions (before anything):** (a) approve lockfile refresh + floor bumps (D-26 as plan-only is already approved; installs are not); (b) root-manifest policy (section 3); (c) TRUST_PROXY value / hosting topology (NEW-18, out of my scope) because it determines the real proxy-addr and ip-address severity.

**Batch 1 - Backend lockfile refresh (non-breaking, highest value):** proxy-addr 2.0.8, axios, follow-redirects, compression 1.8.2, multer 2.5, undici, ip-address, qs, body-parser; raise manifest floors for axios/compression/multer. Regression: `npm audit --omit=dev` in backend must drop to no high/critical; `npm run lint`, `typecheck`, `test:unit`, `test:contract` (backend scripts in CI); integration harness for auth/rate-limit; specific checks: (1) rate limiting still keys per client under the chosen TRUST_PROXY (spoof test: send `X-Forwarded-For` from an untrusted peer; expected to be ignored) - this verifies the proxy-addr fix actually changes behaviour; (2) gzip responses on a large list endpoint (compression); (3) scraper smoke test with mocked `axios.get` (`opportunityScraper` unit test); (4) if the storage router is ever remounted, run an upload test with a 10 MB limit and an aborted upload; (5) JSON body > limit and a malformed gzip body to confirm body-parser still returns 4xx not 500.

**Batch 2 - Frontend non-breaking refresh:** dompurify (latest 3.x), axios, vite (dev), follow-redirects, plus dev-only transitives (json-server tree, source-map-js, postcss-selector-parser). Regression: `npm run lint`, `typecheck`, `build`; browser harness (`run-browser.js`) on the 9 DOMPurify surfaces: note editor, announcement list/detail/form, community page, report form/detail, rendering a seeded `<img src=x onerror=...>` and `<svg onload>` payload to confirm still stripped; login flow (axios interceptors in `lib/api.ts`).

**Batch 3 - Root manifest cleanup (needs the Batch 0 decision):** remove `bcrypt` (minimum). Regression: `npm install`/`ci` at root works; `node start.js`/`npm run dev`, `npm run test:memory` and husky hooks still run; confirm CI still green (CI does not use the root). Audit root again.

**Batch 4 - Semver-major, separate, optional: zod 3 to 4 and react-router-dom 6 to 7.** Low exploitability (zod: none by reading; react-router: moderate and no user-controlled targets found). Recommend deferring behind Batches 1 to 3 and treating as a feature-sized change with its own task and owner approval. Regression if approved: all 8 zod form pages with valid, invalid and empty inputs (especially `z.coerce.number()` in Event/Society forms, `@hookform/resolvers` compatibility); full route walk (all 40 files that import the router), protected-route redirects, deep links, 404, browser back/forward, `Link` and `navigate()` with API-sourced targets (notifications).
