## Part 2 — NEW-14 backup/restore safety review

### 2a. Are password hashes included in plaintext exports? **Yes, confirmed by design.**

`backend/src/scripts/backup.js` performs `db.collection(colName).find({}).toArray()` for every non-system collection, including `users`, and writes the raw result to a JSON file in `backups/` (git-ignored, but filesystem-readable by anything with host/container access). The script's own header comment acknowledges this: "the export is the raw collection contents. That includes the `users` collection with bcrypt password hashes, so the resulting file must be treated as sensitive." There is no redaction, no field exclusion, and no encryption of the output file. File permissions are whatever `fs.writeFileSync` + the process umask produce (no explicit `mode` option) — not forced to `0600`.

**Proposed design fix (plan only):**
1. Encrypt the backup file at rest: after building `backupData`, encrypt the serialized JSON with a key supplied via environment/secret manager (e.g., AES-256-GCM with a key never stored alongside the backup) before `fs.writeFileSync`; `restore.js` decrypts before `JSON.parse`. This preserves full restore fidelity (passwords, tokens, etc. all round-trip) while making a stolen/leaked backup file useless without the key.
2. As a cheaper interim step, set explicit file mode `0o600` on write and document (in `backups/README` or ops runbook) that the `backups/` directory must be excluded from any sync/off-host copy that isn't itself encrypted, until (1) is built.
3. Do not solve this by stripping password hashes from the export — that would silently make the backup non-restorable for login purposes (every user would need a password reset after a restore) without the operator being warned. If the owner decides partial/redacted exports are wanted for non-DR use cases (e.g., analytics), that should be a separate, clearly-named script, not a change to the DR backup.
- This needs owner sign-off before implementation (encryption key management, where the key lives, who can decrypt) — recording as an open question, not deciding it here.

### 2b. Is restore atomic (all-or-nothing), or can it leave a half-restored state? **Not atomic; a half-restored state is possible, confirmed by reading the code.**

`restore.js` `performRestore()`:
- Step 2 (`buildRestorePlan`) does validate and convert the *entire* backup file in memory before any DB write — so a malformed/invalid backup file is rejected before touching the database. That part is safe.
- Step 4, however, loops over `plan` (one entry per collection, up to the 32 `RESTORABLE_COLLECTIONS`) and for each one calls `db.collection(name).deleteMany({})` followed by `db.collection(name).insertMany(documents)`, sequentially, with **no surrounding transaction and no rollback**. Two distinct failure windows:
  - **Within one collection**: if `insertMany` throws after `deleteMany` succeeded (duplicate key, document too large, a dropped connection mid-write, a validator rejecting one document in a large batch), that collection is left **empty** — its old data is gone and the new data only partially (or not at all) written.
  - **Across collections**: if collection #N (of 32) fails this way, every collection processed before #N has already been wiped-and-replaced with backup data, while every collection after #N is untouched (still has its pre-restore data). The database ends up in a mixed state: some collections on "new" (restored) data, one collection empty, the rest still on "old" data. The process then throws and exits via the `if (require.main === module)` catch block, after `mongoose.connection.close()` in `finally` — nothing attempts to undo the partial writes.

**Proposed design fix (plan only, two options, no code change made):**
- **Option A — shadow-collection cutover (works on a standalone MongoDB, no replica set required):** for each collection in the plan, write the restored documents into a temporary collection (e.g. `__restore_<name>`) via `insertMany`, leaving the live collection untouched. Only after *all* 32 temp collections have been fully and successfully populated, perform the cutover: for each collection, atomically swap via `db.collection(name).rename('__restore_<name>', { dropTarget: true })` (each individual rename is atomic in MongoDB). If any temp-population step fails, drop the temp collections and abort — the live data was never touched. This still isn't a single cross-collection ACID transaction (the rename sweep itself takes multiple ops), but it removes the "half-replaced with no old data left" failure mode: a failure during population never touches live collections, and a failure during the rename sweep only reduces the "how many collections got the new data" count — it never deletes a live collection without having already prepared its replacement.
- **Option B — Mongo multi-document transactions:** wrap the whole restore (`deleteMany`+`insertMany` for all 32 collections) in a single `session.withTransaction(...)`. Requires the deployment to run as a replica set (standalone MongoDB does not support transactions) — needs confirming against the actual deployment topology before this is viable; if MongoDB runs standalone in any environment this script targets, Option A is the only one that works there.
- Recommend Option A as the default proposal since it needs no infrastructure assumption; flag Option B only if the owner confirms every target environment is a replica set.
- Either option is a behavior change to a destructive script and needs owner approval before implementation, per CHARTER §2.4 ("never run legacy seed/backup/restore/cleanup scripts without inspecting them and obtaining approval") — this item records the design, not an implementation.

### 2c. Can a legacy report block a backup? **Yes, confirmed by design — and it blocks the entire backup, not just that collection.**

`backup.js`'s `assertBackupCollectionsSupported()` runs before any document is read: it lists every non-system collection in the live database and throws `UNSUPPORTED_COLLECTIONS` (aborting the whole backup, no file written) if **any** of them is not in `restore.js`'s `RESTORABLE_COLLECTIONS` allowlist. `RESTORABLE_COLLECTIONS` only lists the 32 current Mongoose model collections; the retired `server/`-era `reports` collection (referenced in CHARTER §4-8 as a known legacy artifact) is deliberately excluded ("Legacy collections from the retired `server/` models (for example `reports`) are deliberately not included" — restore.js comment). So: if a legacy `reports` collection still physically exists in the target database, **every** backup attempt fails outright with no file produced, until that collection is dropped/migrated or the allowlist is extended — there is no partial-backup fallback.

**Proposed design fix (plan only):**
- Add a second, explicit set — e.g. `KNOWN_LEGACY_COLLECTIONS = ["reports"]` — distinct from `RESTORABLE_COLLECTIONS`. In `assertBackupCollectionsSupported`, skip (log a warning, do not back up) any collection in `KNOWN_LEGACY_COLLECTIONS`, and only abort the backup for collections that are in neither list (i.e., genuinely unexpected/new collections the allowlist hasn't caught up with). This preserves the current fail-safe intent (an unrecognized new collection still blocks the backup rather than silently being dropped) while not letting a *known, already-decided-to-be-excluded* legacy collection block backups indefinitely.
- Alternative, if the owner would rather not carry a second list: resolve the legacy `reports` collection directly (migrate it into `projectreports`/drop it) so the allowlist question disappears. That is a data decision outside this role's scope — recording it as a question for the owner, not deciding it.

## Part 3 — Importer/scraper audit (NEW-24, AUD-030, NEW-25)

### Scraper (`opportunityScraper.js`, `scrapeOpportunities.js`) — SSRF controls reviewed, not weakened, no gaps found

- All server-side fetches go through `backend/src/utils/urlSafety.js`'s `createSafeFetchOptions()`: blocks loopback/private/link-local/metadata (`169.254.169.254`)/CGNAT/documentation/multicast ranges for both IPv4 and IPv6, including IPv4-mapped and NAT64 forms; checks the *resolved* address via a custom DNS `lookup` (defeats DNS-rebinding, since the same lookup result is what the socket connects to) on both the initial request and every redirect hop (`beforeRedirect`); refuses to run at all if an `http_proxy`/`https_proxy`/`all_proxy` env var is set (since a proxy would make the address check unverifiable); bounds redirects (3) and response size (5 MB); sets `proxy: false` on the axios call itself. This is a solid implementation — no change proposed or needed.
- Scrape targets come only from `backend/src/config/opportunitySources.js` (a static, developer-maintained list), not from any user- or request-supplied URL, and the scraper is only invoked via `npm run scrape:opportunities` / `scrapeOpportunities.js` (a script, `assertExplicitTarget`-gated against the DB target), never via an HTTP route. There is no user-reachable attack surface here.
- Scraped links are also filtered through `safeWebUrl`/`isSafeWebUrl` (http/https only, no credentials in the URL, length-bounded) before being resolved and again before being persisted ("belt and braces" double filter in `scrapeAllSocieties`) — stored scrape results can't carry a `javascript:`/`data:` URL.

### Importer routes (`backend/src/routes/importers.js`) — `/slack` and `/todoist`, under `/api/v1/societies/:societyId/importer/...`

Guards confirmed: `authenticate` → `requirePermission('community_hub','create')` → `societyAccessByParam('societyId')` → `requireExistingSociety` (404 on missing society, 400 on malformed ObjectId) applied to both routes via `importGuards`. Slack import validates the *entire* payload (`buildSlackImportPlan`, running every channel/message through the real Mongoose schema's `validateSync()`) before writing anything, so a validation failure can't leave a partial import — this mirrors the backup/restore "validate everything before any write" pattern and is good practice already in place.

Gaps found (read-only observations, no code changed):
1. **No per-request item-count or size ceiling on either route**, beyond the global `express.json({ limit: "10mb" })` body-size cap in `server.js`. A 10 MB JSON payload of short messages/tasks can contain tens of thousands of items; both routes process them in a single sequential `for` loop with one `await Channel.findOne/create` or `await Message.create`/`Task.create` per item — a single request can drive a large number of sequential DB round-trips with no batching and no explicit cap. There is a global rate limiter (`generalLimiter`, applied to all of `/api/v1`) but no importer-specific stricter limit for this comparatively expensive endpoint.
2. **Todoist import (`/todoist`) has no duplicate-import protection at all.** Every call creates a new `Task` per item in `req.body.tasks`; re-submitting the same export (retry after a timeout, double-click, re-import) creates full duplicates with no idempotency key (e.g. an external Todoist task ID) and no "already imported" check.
3. **Slack import deduplicates channels by `(societyId, name)` but not messages.** `buildSlackImportPlan`/the route handler re-create every message in `entry.messages` on each call; re-running the same Slack export against the same channel duplicates every message (no external message ID/timestamp is used as a dedupe key, even though Slack exports normally carry one).
4. **No explicit duplicate-society-import lock**: nothing prevents two concurrent `/slack` or `/todoist` imports for the same society from racing (e.g., both creating the same-named channel before either commit — `findOne` then `create` is a check-then-act race, not an atomic upsert). Low severity (requires concurrent duplicate imports to matter), but worth a test case.

**Proposed fixes (plan only):**
- Add a per-request item cap (e.g. reject `channels.length + messages.length > N` or `tasks.length > N` with 400, independent of the 10 MB body limit) and consider a dedicated, stricter rate limit for `/importer/*` given it's a write-amplifying endpoint.
- Todoist: require/accept an external ID (Todoist's own task `id`) and upsert (`Task.findOneAndUpdate({societyId, externalId}, {...}, {upsert:true})`) instead of unconditional `create`.
- Slack: use `Channel.findOneAndUpdate(..., {upsert:true})` instead of find-then-create to remove the race, and dedupe messages by a stable key if the Slack export format provides one (e.g. `ts`); if it doesn't, this may need a product decision on whether re-import should be idempotent at all — flagging rather than deciding.

### Stored URL fields never validated (NEW-25) — confirmed, four fields

`urlSafety.js` provides `safeWebUrl`/`isSafeWebUrl` and is used for scraped opportunity links, but **none of the following four schema fields are run through it, or through any mongoose `match`/`validate`, before being persisted** — each is a plain `String` accepted straight from `req.body`:

| Field | Model | Route that sets it | Validation found |
|---|---|---|---|
| `avatarUrl` | `User` (`backend/src/models/User.js:33`) | `PATCH` in `backend/src/routes/users.js:135-137` (`if (avatarUrl !== undefined) user.avatarUrl = avatarUrl;`) | none |
| `logoUrl` | `Society` (`backend/src/models/Society.js:54`) | `PATCH /api/societies/:id/logo` (`backend/src/routes/societies.js:214-222`) | none |
| `logoUrl` | `Institution` (`backend/src/models/Institution.js:13`) | `PATCH /api/institution/logo` (`backend/src/routes/institution.js:42-58`) | none |
| `imageUrl` | `Message` (`backend/src/models/Message.js:14`) | `channels.js:339-394` (message create/attachments), `channels.js:485-521` (reply), `conversations.js:219-248` (DM message) | none |

None of these are ever fetched server-side (no SSRF exposure — confirmed by grep, no `axios`/`fetch`/`http` call reads from these fields), but they are stored verbatim and rendered client-side (presumably as `<img src>`/avatar/logo displays, and `imageUrl` possibly also as a clickable attachment link in chat). Risk: a user can store a `javascript:`/`data:`/arbitrarily long string in any of these four fields; if any frontend code ever renders one of them as an `<a href>` (vs. strictly `<img src>`) rather than purely as an image source, a `javascript:` URL would execute on click (stored XSS vector via a non-fetch path). Even restricted to `<img src>`, unbounded length / non-URL garbage is a minor data-integrity and front-end–breakage risk. I did not inspect the frontend rendering code for these fields (out of scope / read-only, and not requested) — the finding here is the backend-side absence of validation, which is NEW-25's scope.

**Proposed fix (plan only):** apply the existing `isSafeWebUrl`/`safeWebUrl` helper (already built and tested for the scraper) as a mongoose `validate` function on these four fields, rejecting non-http(s), credentialed, or oversized values at the model layer — the same helper, no new validation logic needed. This is a small, consistent, low-risk fix once approved; not implemented here per scope (no code changes).
