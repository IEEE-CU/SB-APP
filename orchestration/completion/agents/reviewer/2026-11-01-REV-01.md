## 2. 384ce8a - Gemini server-side, channel wrappers removed

Scope: 15 files; AUD-013, D-B1..B4, D-B10/B11. `channels.ts` removal of `addMember` / `removeMember` matches D-B1(a); the new node test asserts every service call has a backend route. `@google/genai` stays installed (D-B4); no manifest/lockfile change (confirmed: diff of package*.json across the range is empty).

D-B10 (no transaction data in the prompt), confirmed by reading `financialSummary.js` and the prompt builders: the only data in the prompt is clipped society name, short name, budget and a balance. Transactions are touched only through `Transaction.aggregate` (sum per society/type, APPROVED only); no `find`, no description/category. The unit test makes `Transaction.find` throw and checks the outbound body for EXPENSE/INCOME/description/category. **Caveat to put to the owner:** the balance is a transaction-derived aggregate sent to Google. The old page sent a society-list balance of the same kind, so I judge it compatible with D-B10, but the wording "no financial transaction data" is the owner's; they should confirm that aggregate balances/budgets are acceptable. The single-society prompt no longer lists transactions at all (old prompt sent none either).

D-B11 (legacy ADMIN passes, others need finance:view), confirmed in `routes/ai.js`: `adminOrFinanceView` lets `user.role === "ADMIN"` through without an RBAC role and gives it `scopeFilter {}`; everybody else goes through `requirePermission("finance","view")` then `attachScope("_id")`. `validateRequest` runs after scope and before the rate limiter: only `societyId` accepted (24-hex string), scope check 403 before existence 404 (no probing), `aiLimiter` 10 per 15 min per user id, mounted after the permission check. API key: read only in `config/gemini.js`, sent in a header, errors reduced to a status number. Fail-closed scope: users without a society scope get the filter `{_id:"000...0"}` so they see no societies (404 "No societies in scope" / 403 for explicit id).
Note: BATCH2_DECISIONS.md still lists D-B10 and D-B11 as open questions with different wording (D-B11 there asked "accept 403 for legacy admin?"); the DECISION-REGISTER and CHARTER 18 record owner requirements that reverse it. I rely on the charter/register; I could not see the owner's original message.

Removed / changed assertions: none in existing tests (all test files in this commit are new). Removed production behavior: frontend `getFinancialInsights(state, id)` signature and the `FinancialStateSummary` export (grep of the diff shows its only user, AiAuditPage, was updated); `addMember`/`removeMember`.

Could break / concerns:
- **Model change:** the frontend used `gemini-3-flash-preview`; the server default is `gemini-1.5-pro` unless `GEMINI_MODEL` is set. 1.5-pro may be retired by the provider; deployment must set `GEMINI_MODEL`/`GEMINI_API_KEY` or the feature returns the "not available" 503. Request a decision/documentation line; not a code defect.
- `/ai` router is newly mounted in routes/index.js. The register's "dormant AI router activation not approved" refers to the baseline; D-B3(a) authorizes this endpoint, so I consider it in scope.
- `GEMINI_BASE_URL` is configurable by environment only (not user input); acceptable, but it is an outbound-request target - keep it out of untrusted config.
- Rate limiter keyed by user id is per process (D-04 multi-instance, pre-existing limitation).
- Browser spec watches for Google hosts and stubs 200/503/429 at the network edge; the backend path with a configured key is only covered by the fake-fetch unit test, never against a real provider (cannot be, by design).
Changes requested: record the model/env requirement; owner confirmation of the D-B10 aggregate caveat.
